# SEQUENCE27 Approach Draft

## 문서 상태
- 상태: `초안`
- 본 문서는 확정 설계가 아니다.
- 목적: 현재 맵 조건에서 `Sequence27` 접근 로직 후보를 비교하고, 후속 구현 시 검토 기준을 남긴다.

## 문제 정의
현재 `Sequence27`의 접근 단계는 `Sequence27ApproachComponent`에서 각 AI가 `MoveToActor(Target)`로 플레이어 본체를 직접 추적하는 구조다.

현재 맵 조건은 아래와 같다.
- 기본 복도 폭은 직사각형 형태로 일관됨.
- 하지만 복도 위에 배경 소품 오브젝트가 다수 배치되어 있음.
- 결과적으로 실제 NavMesh가 유지되는 유효 폭은 위치마다 달라짐.
- AI 3기 이상이 비슷한 방향/위치에서 동시에 플레이어에게 접근하는 상황이 존재함.

현재 관찰된 문제는 아래와 같다.
- 여러 AI가 동일한 목표점(플레이어 본체 1점)으로 수렴함.
- 앞 AI와 뒤 AI, 소품 오브젝트가 동시에 병목을 만듦.
- `MoveTo`가 성공 상태여도 마지막 접근 구간에서 실제 진전이 거의 없음.
- 현재 fallback/direct move/timeout 의존도가 높아질 수밖에 없음.

즉, 이 문제는 단순 수치 조정만으로 해결하기 어려운 `접근 구조 설계` 문제로 본다.

## 현재 구조 요약
대상 코드:
- `Source/Dev_THESEUS/Public/Sequence/Sequence27ApproachComponent.h`
- `Source/Dev_THESEUS/Private/Sequence/Sequence27ApproachComponent.cpp`

현재 구조의 핵심:
- 모든 유닛이 `TargetActor`를 직접 목표로 삼음.
- `MoveToActor(Target)`를 사용함.
- 유닛별 상태 구분(선두/후속/대기)이 없음.
- stuck 감지 시 `DirectMoveFallback` 사용.
- 완료 조건은 `EncircleTriggerDistance` 내 유닛 수 기준.

현재 구조의 강점:
- 구현이 단순함.
- 넓은 공간/단순 네비 환경에서는 빠르게 동작함.

현재 구조의 약점:
- 좁은 복도/가변 유효 폭 환경에 취약함.
- 다수 AI가 동시에 접근할수록 병목이 심해짐.
- 직접 추적 구조상 서로 밀고 끼는 현상이 구조적으로 발생함.

## 맵 조건 정리
이번 `Sequence27` 설계는 아래 맵 조건을 전제로 검토한다.

1. 기본 복도 형상
- 직사각형 복도형 구간.
- 큰 방향성은 단순한 일자/꺾임 기반으로 유지.

2. 실제 네비게이션 조건
- 소품 배치 때문에 유효 Nav 폭은 위치마다 달라짐.
- 어떤 위치는 1열만 가능하고,
- 어떤 위치는 2열 비슷하게 보일 수 있으며,
- 어떤 위치는 목표점 근처가 소품 때문에 실질적으로 막힘.

3. AI 접근 형태
- AI는 3기 이상이 동시에 개입 가능.
- 대체로 비슷한 측면/전방 방향에서 들어옴.
- 완전한 원형 포위보다 `압박 접근` 성격이 강함.

## 설계 후보 비교

### 후보 A. 현재 방식 유지 + 수치 튜닝
개념:
- `MoveToActor(Player)` 유지.
- `ApproachAcceptanceRadius`, `EncircleTriggerDistance`, `StuckTickThreshold`만 조정.

장점:
- 구현 비용이 가장 낮음.
- 기존 BP 연결을 거의 건드리지 않음.

단점:
- 목표점이 여전히 1점으로 고정됨.
- 좁은 구간에서는 충돌/끼임의 원인을 제거하지 못함.
- timeout 의존이 계속 남을 가능성이 큼.

판단:
- 임시 응급처치로는 가능하지만, 구조 해결책으로는 부적합.

### 후보 B. 원형/반원형 포위 슬롯 방식
개념:
- 플레이어 주변 원형/반원형 슬롯을 만들고 각 AI가 서로 다른 슬롯으로 이동.
- `MoveToLocation(Slot)` 기반.

장점:
- 넓은 공간에서는 매우 효과적.
- 동일 지점 수렴 문제를 해결함.
- 포위 연출이 명확해짐.

단점:
- 현재 맵은 좁은 복도 기반이라 원형 포위가 자연스럽지 않을 수 있음.
- 유효 Nav 폭이 좁은 위치에서는 다수 슬롯이 무효가 될 가능성이 큼.
- 구현 대비 실제 이득이 제한될 수 있음.

판단:
- 넓은 공간용 설계로는 적합.
- 현재 복도형 `Sequence27`의 1차 해법으로는 우선순위 낮음.

### 후보 C. 복도형 대기열 접근 방식
개념:
- 동시에 접근하는 AI 수를 제한.
- 선두 1기 또는 2기만 실제 접근.
- 나머지는 앞 유닛 뒤의 대기 슬롯으로 이동.
- 선두가 도달/정지/이탈하면 후속 AI가 순차 승격.

장점:
- 현재 복도형 구조와 가장 잘 맞음.
- AI가 같은 목표점으로 몰리지 않음.
- 병목이 있어도 줄세우기 형태로 관리 가능.
- 소품이 많아도 `선두 슬롯 + 후속 대기 슬롯`만 안정적으로 유지하면 됨.

단점:
- 전면 압박은 자연스럽지만, 완전 포위처럼 보이지는 않음.
- 유닛별 상태 관리(선두/대기/도달/실패)가 필요함.

판단:
- 현재 맵 조건에서는 가장 현실적인 주 설계 후보.

### 후보 D. 가변 슬롯 + 대기열 혼합 방식
개념:
- 기본은 복도형 대기열 접근.
- 단, 플레이어 근처 현재 위치의 유효 Nav 폭을 보고 1열/2열을 동적으로 결정.
- 가능한 경우 2기까지 전면 접근, 아니면 1기만 접근.
- 나머지는 뒤 대기열 유지.

장점:
- 현재 맵의 “복도 폭은 같지만 실제 유효 Nav 폭은 다름” 조건에 가장 잘 맞음.
- 너무 복잡한 포위 계산 없이도 유연성이 생김.
- 위치에 따라 1열/2열을 자연스럽게 전환 가능.

단점:
- 후보 C보다 구현 복잡도가 높음.
- 슬롯 계산/재평가 주기를 잘못 잡으면 불안정해질 수 있음.

판단:
- 현재 기준 최우선 검토 후보.
- 실제 구현은 후보 C를 기반으로 하고, 2열 가능 구간만 확장하는 식이 적절함.

### 후보 E. 스플라인 기반 강제 접근
개념:
- AI 접근 경로를 스플라인으로 고정.
- 길찾기 대신 연출 레일 기반으로 이동.

장점:
- 연출 통제가 쉽고 재현성이 높음.
- 장애물 많은 맵에서도 보이는 결과를 강제로 만들기 쉬움.

단점:
- 플레이어 위치 변화에 유연하게 반응하기 어렵다.
- 맵 수정 시 관리 비용이 큼.
- 여러 AI/가변 상황에 대응하기 어렵다.
- 복도 내 압박보다는 scripted movement에 가까워질 위험이 큼.

판단:
- `Sequence27` 전체 접근 본체로는 부적합.
- 특정 등장 구간, 특정 회피 구간, 1회성 연출 이동에는 보조 수단으로 검토 가능.

## 현재 기준 추천 방향
현 시점에서 추천 우선순위는 아래와 같다.

1. 주 설계 방향
- `복도형 대기열 접근`을 기본으로 한다.
- 즉, 전원 동시 플레이어 직접 추적을 버리고,
  `선두 접근 + 후속 대기열` 구조로 전환한다.

2. 확장 방향
- 여기에 `가변 슬롯` 개념을 붙여,
  플레이어 근처 현재 구간의 유효 Nav 폭을 기준으로
  `1열` 또는 `2열`까지 동적으로 허용한다.

3. 보조 수단
- 스플라인은 전체 구조 대체 수단이 아니라,
  특정 구간 scripted movement가 필요할 때만 제한적으로 사용한다.

## 추천 동작 개념
### 기본 개념
- 플레이어 본체를 모든 AI의 직접 목표로 삼지 않는다.
- 플레이어 앞 접근점 1개 또는 2개를 만든다.
- 그 뒤에 대기 슬롯을 순차적으로 만든다.
- AI는 자신에게 배정된 슬롯으로 이동한다.

### 예시
현재 위치가 좁아 1열만 가능한 경우:
- `FrontSlotCenter`
- `QueueSlot1`
- `QueueSlot2`
- `QueueSlot3`

현재 위치가 조금 넓어 2열이 가능한 경우:
- `FrontSlotLeft`
- `FrontSlotRight`
- `QueueSlot1Center`
- `QueueSlot2Center`

핵심:
- 전면 접근 가능 수만큼만 실제 활성 접근 AI를 둔다.
- 나머지는 뒤 대기열에서 관리한다.

## NavMesh 운용 메모
현재 조건에서 중요한 것은 “복도 전체를 넓게 덮는 것”이 아니라,
`선두 슬롯 + 후속 슬롯`이 연속적으로 살아 있는 것이다.

운용 원칙:
- 작은 배경 소품은 가능하면 `Can Ever Affect Navigation` 비활성 검토.
- 실제 길막 의도가 있는 큰 오브젝트만 Nav를 carve 하게 유지.
- 플레이어 근처 최종 정지 구간의 Nav 연속성을 우선 확인.
- 뒤 대기 슬롯 2~3칸 정도가 살아 있는지 확인.

즉, 현재 맵에서는 “넓은 전투용 NavMesh”보다 “연속된 압박용 슬롯 체인”이 중요하다.

## 미정 항목
아래는 아직 확정하지 않는다.
- 전면 동시 접근 허용 수: `1` 고정인지, `1~2` 가변인지
- 슬롯 간격 값
- 플레이어 정면 기준으로만 접근할지, 측면 오프셋을 일부 허용할지

- 접근 실패 시 후퇴 후 재시도 여부

## 현재 결론
현재 맵 조건에서는 아래와 같이 정리한다.
- `MoveToActor(Player)` 전원 직접 추적 구조는 부적합.
- 원형 포위 슬롯 구조는 현재 복도형 상황의 주 해법으로는 우선순위 낮음.
- 가장 현실적인 방향은 `복도형 대기열 접근`.
- 최우선 검토 후보는 `가변 슬롯 + 대기열 혼합 구조`.
- 본 문서는 초안이며, 구현 확정 전 재검토가 필요하다.
